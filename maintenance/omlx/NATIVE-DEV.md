## 维护边界

普通 AppleScript Quit/Cmd-Q 被上游设计为隐藏窗口，会返回取消；
这不等同于用户拒绝维护。正常维护应先确认 active/waiting 均为零，
通过官方 `omlx-cli stop` 停止后端，再正常终止已核实身份的 App。
重新打开确定的 App 路径，等待健康状态及固定模型实际加载完成。

长提示内存估算包含持久 KV 和临时计算空间；历史约 40GB 增量主要是
大预填充块的临时空间。SSD 前缀复用能减少重复预填充和保留重启缓存，
不能据此保证所有 1M 上下文及多路并发组合永不触发真实内存上限。
不得通过虚报估算、关闭保护、调高上限或截断上下文来制造通过结果。

## 2026-10-20：路由预检查和 GLM 临时内存修复

真实日志中的 21 万 token 对话已有约 21 万 token 前缀缓存，
但 HTTP 路由预检查始终按 `cached_tokens=0` 计算。原始 GLM
估算还将整个 4096 行预填充块按全部注意力头展开计费，而 M3
融合内核直接输出合并头的分数；非融合路径使用 512 行子块。
非融合路径的延迟计算图又会保留多个子块的中间矩阵。

`prepare-preflight-cache-fix.py` 生成五份可审查的源代码覆盖与 diff：

- 仅纯文本路由查询真实前缀缓存；将 SSD 缓存恢复所需内存加入估算。
  请求执行前仍重新恢复、验证缓存，保留实际准入和逐块保护。
- 非融合 GLM indexer 每个子块完成合并分数后释放全头矩阵，
  不改变数学运算、精度、上下文、外层预填充块或原生融合路径。
- 估算保留四份 512 行全头临时量及分数输出；其余 KV、MoE、
  GDN、latent attention 和安全余量原样保留。

实际 M3 Ultra 上，4096 行、8192 pooled keys 的非融合路径交替运行六次：
结果索引哈希完全一致；稳定峰值从约 2.997GB 降到 0.657GB，
同机暖运行从 0.276–0.310 秒降到 0.140–0.163 秒。
这是隔离内核测量，不能代表所有整模型负载的性能。

### 补丁部署及升级边界

签名 App 本体没有修改。覆盖文件安装在：
`~/llmserver/servers/omlx/maintenance-20261020/preflight-fix`。
原生 App 的 `OMLX_PYTHON_OVERRIDE` 指向该目录内的启动包装器；
`local.omlx.gui-autostart` 登录项重新打开原生 App，仍由 App 管理后端。
`preflight-sitecustomize.py` 在每次 Python 启动时核验 M3 Ultra 机型、
五份上游原文件 SHA-256 及五份覆盖文件 SHA-256；不匹配则明确拒绝加载。

**升级会影响补丁，不能直接跨版本套用。** 先下载并验证新版签名，
在停止现有服务之前比较五份上游文件及修复逻辑。若上游已修复，
删除对应覆盖并复测；若上游仍有问题，重新审查、生成覆盖和 manifest，
执行内核等价/内存测试、真实长输入、完整对话续接、重启缓存回归。
未完成这些检查，不用新版替换正在服务的 App。当前旧版
`update-dev.py` 不支持这个原生 App/包装器布局，不能用于自动升级。

恢复官方无补丁启动时，先确认 active/waiting 为零，再停止后端和
已核实身份的 App；恢复 `gui-autostart-before.plist` 到原登录项，
执行 `launchctl unsetenv OMLX_PYTHON_OVERRIDE`，重新注册登录项并打开
`/Applications/oMLX.app`。这会撤销补丁，原内存拒绝问题可能恢复。
不要在存在运行请求时切换解释器或覆盖文件。

这组测试没有覆盖全部 1M 上下文和四路并发组合；真实物理内存不足时，
保护仍应拒绝请求。不能承诺任何长度、并发和系统负载下永不报错。
