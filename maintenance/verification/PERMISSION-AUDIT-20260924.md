# OctoCode 权限执行核对（2026-09-24）

## 当前实际行为

| 界面档位 | Host / harness | 可写入 | 已验证边界 |
| --- | --- | --- | --- |
| 完全 | `bypassPermissions`，完整工具集 | 是 | 真实 Host＋harness 探针在隔离目录内写入成功。 |
| 完全＋本轮明确只读 | 档位仍为 `full`；本轮只暴露 `read_file`、`list_dir`、`grep` | 否 | 强制诱导执行终端写入被拒；同一会话下一轮明确要求写入后成功。正式 UI 的本地 Qwen 只读任务仍持久化 `full`，268 个项目文件哈希无变化。 |
| 审查 | 当前安全降级为只读 | 否 | 强制写入被拒。交互式逐项审批尚未接通，不得称为“变更前询问”。 |
| 目录 | 当前安全降级为只读 | 否 | 原 `auto` 模式可写出工作区，已由真实探针复现；现已阻断。目录级写入隔离尚未实现。 |

权限档位只表示用户授予的上限。明确只读要求作为**本轮任务约束**传给 Host 和 Workbench MCP，不更改界面档位或会话保存的权限；下一轮重新依据新要求判断。若同一轮先要求只读检查、再明确要求修复，保留写入能力以完成后续阶段。对话中没有明确只读标记时，Host 规则仍要求先遵守本轮具体任务，不把全权限误解为必须执行写入。

## 已逐项检查的入口

- Host 原生工具：本轮只读时用允许列表限制读取工具，同时禁用 `use_tool`、`search_tool`；普通完全档位保留完整工具。
- Workbench MCP：Bearer token 绑定活动任务；Host runtime API 的 `write` / `execute`、`supervisor_checkpoint`、VS Code 原生工具与环境安装、非可信 MCP 工具、DAP 执行、代码重命名与浏览器点击/输入/脚本执行，均受档位或本轮只读约束。可信且声明只读的 MCP 工具可读取。
- 旧的全局 `chat.tools.global.autoApprove=true` 已从正式安装和测试实例中关闭；扩展不再根据并发任务反复修改该全局设置。

## 验证与未完成项

- `cargo test -p octocode-host --lib`：42/42；权限相关 Vitest：72/72；Provider：76/76；OpenAI 兼容界面：22/22；TypeScript 类型检查和变更文件 ESLint 通过。
- 正式安装版在交互桌面启动；运行中的 Host 与扩展产物哈希匹配。界面显示 Qwen 上下文 262,144，并完成一次模型列表刷新。真实只读任务使用读取工具且未更改 268 个项目文件。
- **未完成：** 审查档位的逐项用户审批需要 ACP 双向交互；当前使用的 headless `streaming-json` 不提供双向审批。目录档位需要可验证的工作区隔离，单靠 `--cwd` 或模型分类器不能限制终端写出目录。在两项机制实现并跑通真实越界/拒绝/批准测试前，必须继续保持只读并显示当前限制。
- 只读指令识别是明确措辞的词法保护；含糊表达仍依赖模型遵守系统规则。若要求覆盖所有自然语言措辞，应增加独立的本轮只读界面开关。
