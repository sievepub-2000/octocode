# Octocode Auto-Research Target Template

> 目标：持续把 Octocode 迭代成在功能和性能上都优于同类产品的 AI 编程工具。
> 对标对象：Claude Code、Codex CLI、Cursor、ClawCode，以及后续新增的同类工具。

---

## 1. 总目标

- 功能目标：每个可比较模块都至少达到同类最佳实现，并在关键链路上提供额外能力或更低操作摩擦。
- 性能目标：每个可测量链路都在本地基准、回归脚本和真实 WebUI 验证中达到或超过对标工具的当前水平。
- 交付目标：任何新能力都必须同时有正确性验证和性能验证，不能只实现功能表面。

## 2. 淘汰机制

一个模块只有在同时满足下面两个条件时，才可判定“超越对标”并保留：

1. 功能淘汰：
   - 支持的核心子能力不少于当前最佳对标。
   - 用户完成同一任务的操作路径不更长。
   - 至少有一项明确优于对标的差异化能力。
2. 性能淘汰：
   - 同场景下平均延迟、P95 延迟、失败率、资源占用四项里至少三项优于对标。
   - 不得通过牺牲正确性、稳定性或安全性换取表面性能。

如果任一条件不满足，则该模块状态必须标记为：

- `追平中`：功能或性能达到同级，但还未超过。
- `错误领先`：功能看起来更多，但失败率、回归、权限或一致性未达标。
- `性能倒挂`：功能可用，但吞吐、延迟或资源占用落后。
- `待淘汰方案`：连续两轮迭代未改善，需替换方案而非继续打补丁。

## 4. 每轮 autoresearch 必做项

每一轮都必须完成以下闭环：

1. 建立基线：记录当前实现、对标对象、验证命令、关键指标。
2. 提出假设：明确这轮改动想提升什么，如何被证伪。
3. 最小实现：只改最靠近控制路径的代码。
4. 正确性验证：单测、回归、真实 WebUI、错误面检查。
5. 性能验证：至少一项耗时、吞吐或资源指标对比。
6. 保留或丢弃：
   - 通过则纳入基线。
   - 未通过则回滚思路，换更小或更根本的方案。

## 5. 正确性门槛

- 新能力没有自动验证时，不算完成。
- 任何新增 provider、tool、hook、session 行为，必须至少覆盖：
  - 成功路径
  - 错误路径
  - 权限/降级路径
  - WebUI 可见性

## 6. 性能门槛

- 新增逻辑不能让非 provider 本地路径显著退化。
- 优先优化这些路径：
  - runtime bootstrap
  - provider health probing
  - session load/save
  - tool dispatch
  - UI snapshot generation
- 每一轮至少要有一项明确的性能动作，例如：
  - 缓存
  - 避免重复 I/O
  - 避免重复 provider probe
  - 降低 snapshot 序列化成本
  - 缩小事件/会话扫描范围
